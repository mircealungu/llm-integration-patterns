# LLM Output Provenance

*Tag every stored LLM artifact with the model and prompt that made it.*

## Context

LLM-generated artifacts are written to persistent storage and reused for a long time, while the models and prompts that produce them keep improving. The prompts live in the code, next to the calls that use them. The prompt and the model change independently of each other, and a change to either can have a large effect on output quality.

## Problem

When a prompt or model improves, how can exactly the stale artifacts be found and regenerated, without reprocessing the entire store?

## Problem in Zeeguu

When a learner saves a word, Zeeguu saves it in the form the learner met it in a text, for example the German *Rabatten* (discounts). Zeeguu then shows example sentences for the word, generated by an LLM and stored, so every learner of the word sees the same sentences.

The prompt, version `v3`, told the model to use the word exactly in that form, even where the sentence needed another one. So one stored sentence offered *hohe Rabatten* (high discounts), where German grammar needs *hohe Rabatte*. In October 2026 a new version of the prompt, `v4`, fixed this for new sentences.[^prov-v4] But the store already held more than a hundred thousand sentences. Which of them came from `v3`?

## Forces

- **Regenerating everything is wasteful.** Most stored outputs would not change under the new prompt, and every regeneration costs a call. Some outputs have also been seen by users already, and would change under them. *(pushes toward regenerating only part of the store)*
- **The timestamp seems enough.** Every row records when it was created, and the code history says which prompt was deployed when. Recording more for every output costs schema changes and care on every write. *(pushes toward recording nothing more)*
- **The request logs exist already.** An LLM gateway or the provider's dashboard records every call with its prompt and model. Storing the same facts again next to every output looks like duplication. *(pushes toward relying on the logs)*
- **The deployed configuration is not always what ran.** A fallback (a backup model, called when the main one fails) can answer from another provider, and two prompts can be live at once during an experiment. *(pushes toward distrusting what the deployment history says)*
- **Prompts change by small edits.** Rewording a line in place is quick, and naming every edit as a new version feels like ceremony. *(pushes toward editing prompts in place)*

## Solution

Store with every LLM-generated artifact a record of what produced it: the model, the prompt version, and when. This record is the artifact's *stamp*. Keep each (model, prompt version) pair once, in a shared generator table, and have every artifact point at its row. Request logs cannot replace the stamp: they are kept apart from the outputs, so a database query for stale outputs cannot see them.

Regeneration then becomes a query. It can be as broad as *"everything produced by prompt v2"*, or as narrow as one (model, prompt) pair. When a prompt does well on one model and poorly on another, only that combination is redone. The same query works across every kind of artifact at once.

Record the model that actually answered, not the one the configuration names. Use the same model identifier that the system uses to choose the model, kept in one place (*Centralized Model Selection*), so the stamp and the selection always name the same model.

Give each prompt a version name, and a new one whenever its text changes. A version in the prompt's file name, or a hash of the prompt text, makes this hard to forget. A stamp that stays the same while the prompt changes gives two different prompts the same name, and queries built on it return the wrong rows.

## Solution in Zeeguu

Zeeguu keeps a table of generators, each a model name and a prompt version. Example sentences, simplified articles and audio lessons all point at it.[^prov-entity] A single query found every sentence written by `v3`. Those that no learner was using were deleted, and new ones come from `v4` when a learner next needs them. Those in use stayed.

![[llm-output-provenance-diagram.svg]]
*Provenance as Zeeguu stores it. Each example sentence keeps its own timestamp and points at a shared `ai_generator` row naming the model and prompt version that produced it. The sentence from prompt `v3` (red) is found by a query on that table.*

Here the date alone would have worked too, because `v4` replaced `v3` on a single day. In general it is not enough. For more than a year, `v3` sentences were written by DeepSeek and by Claude at the same time, and the *Rabatten* sentence came from DeepSeek. Only the stamp tells them apart.

Not every artifact is stamped this well. Simplified articles record the model but not the prompt version, so a change to the simplification prompt cannot be traced in the stored articles.

[^prov-entity]: `AIGenerator` (`model_name`, `prompt_version`) in `zeeguu/core/model/ai_generator.py`, and the tables that reference it, in the `zeeguu/api` repository.
[^prov-v4]: The `v4` prompt: `zeeguu/core/llm_services/prompts/example_generation.py`, commit `b8bd9eb0`, in the `zeeguu/api` repository.

## Consequences

- **Selective regeneration becomes a query.** Re-run everything a given prompt or model produced and leave the rest. The same record shows which model and prompt wrote what, for audits and for comparing them.
- **The guarantee lasts only as long as the discipline.** Every write path must stamp, including new kinds of artifacts added later, and every prompt edit must change the version. A stamp that drifts from what actually produced the artifact quietly returns the wrong rows.

## War Story: The Nine Hundred Lessons

The audio lessons were not always stamped. Each lesson teaches one word. A teacher voice asks the learner to say something in German:

```text
Teacher: How would you say you need at least ten minutes? [5 seconds]
```

But a learner who only hears the audio cannot know which of these to say:

- *Ich brauche mindestens zehn Minuten* (I need at least ten minutes)
- *Du brauchst mindestens zehn Minuten* (you need at least ten minutes)

In May 2026 the prompt was fixed. But about nine hundred stored lessons already had questions like this one.

![[llm-output-provenance-problem.svg]]
*How Zeeguu stored audio lessons before the stamp. Every lesson carried the same label, whatever prompt had written it. The lessons with the ambiguous question (red) could only be found by their text.*

Every lesson carried the same label, `claude-v1`, and the prompt file had been edited in place many times. Nothing said which lessons came from which prompt. The nine hundred were found only by searching the scripts' text for the ambiguous phrasing. A label that does not change when the prompt changes records nothing.

Care alone had not kept the versions honest, so the check moved into the build. A CI job now keeps a hash of the text of every versioned prompt. It fails when the text of a prompt changes but its version name stays the same.[^prov-ci]

[^prov-ci]: `tools/check_prompt_versions.py` and `.github/workflows/prompt-versions.yml` in the `zeeguu/api` repository.

## Known Uses

- *Better attested in tooling than in production self-reports.* The capability is productized: [MLflow Prompt Registry](https://mlflow.org/docs/latest/genai/prompt-registry/) and [LangSmith](https://docs.langchain.com/langsmith/prompt-engineering-concepts) version prompts and record which prompt/model produced each output, confirming the pattern's core claim that the *prompt* deserves versioning as much as the model, but these are tools, not documented in-app deployments.
- *Adjacent production pipelines.* [DoorDash](https://careersatdoordash.com/blog/doordash-profile-generation-llms-understanding-consumers-merchants-and-items/) stores versioned LLM-generated profiles and "treat[s] prompts as code"; [Etsy](https://www.etsy.com/codeascraft/understanding-etsyas-vast-inventory-with-llms) stores Pydantic-validated LLM attribute extractions over 100M+ listings. Both store LLM artifacts at scale and version prompts, but neither publicly describes stamping *each artifact* with its prompt version to drive *selective* regeneration, which is the key mechanism here. We did not find a first-hand account of the full pattern, so Zeeguu is our instance.

## Related Patterns

*LLM Content Validation Tracking* records whether an artifact has been confirmed. Provenance records how it was made. Together they say which artifacts to trust and which to regenerate.

*Centralized Model Selection* keeps the model identifier in one place. The stamp should use the same identifier.

*Rent, Then Build* trains a cheaper replacement on labels an LLM produced. Provenance lets it leave out the labels from a prompt version later found to be noisy or biased.

*Soft Invalidation of LLM Artifacts* takes over once provenance has found the stale outputs: it retires them from reuse while the old references that learners already heard keep working.

*Reject and Reprompt* records a refusal with the prompt version, so the system does not ask again until the prompt changes. That record relies on the same versioning of prompts.
